## 2. Target architecture

Package name, bundle entry and component name are shown as
`@openpowershift/oscd-menu-remove-ieds`, matching the target GitHub repository.
If Q1 is answered "keep the current name", only the names and URLs change; the
structure does not.


Component rules:

- Root component owns dialog state and dispatches edits. It does not build
  labels, impact sets or summaries; those come from `foundation/`.
- `foundation/removal-checks.ts` remains pure and DOM-read-only.
- `foundation/removal-plan.ts` returns the `EditV2` sequence (one `Remove`/
  `SetAttributes` list per IED, plus the SubNetwork/Communication removals) and
  the `RemovalSummary`. The root only dispatches them with the title
  `Remove IEDs`; the first is a new undo entry and later ones are squashed.
- Every user-visible string is `msg()` or `msg(str\`...\`)` from
  `@lit/localize`. No literals in templates, `aria-label`, `title` or status
  text.
- `theme.ts` maps `--oscd-theme-*` to internal `--oscd-*` on `:host`, and
  `oscdPaletteMd3` points the Material tokens at the internal palette. The
  confirmation component inherits the palette; it does not redeclare it.
- `:host` is a flex column with `height: 100%` and the content area uses
  `flex: 1 1 auto; min-height: 0`. Dialog sizes use `dvh`/`vw` caps without
  `calc(100vh - Npx)`.
- Unit tests use `src/testing/plugin.ts` and `src/testing/driver.ts`, never
  private fields. Screenshot tests use the same helpers and `visualDiff`.

## 5. Test strategy

### 5.1 Helpers

- `src/testing/plugin.ts`: defines the plugin tag once, mounts it in a host of a
  requested height, listens for `oscd-edit-v2`, applies each edit with an
  `XMLEditor` (including `squash`), bumps `docVersion`, and exposes `edits`,
  `editor`, `settle()`, `applyEdit()` and `unmount()`.
- `src/testing/driver.ts`: the only DOM-aware test file. It exposes
  `open()`, `close()`, `select(names)`, `search(text)`, `remove()`,
  `confirm()`, `review(section)`, `options()`, `summary()` and `dialogOpen()`.
  Specs never query `shadowRoot` or call private methods.
- `src/testing/fixtures.ts`: loads `test/fixtures/*.scd` with `fetch`, and
  `dom.ts` provides deep shadow queries and slot text.
- No fixed waits, `setTimeout`, pixel coordinates or `Object.defineProperty`.
  Wait for `updateComplete`, `opened`, `closed`, or `waitUntil(condition)`.

### 5.2 Unit and component tests

| Area | Tests |
|---|---|
| `foundation/ied-description.ts` | manufacturer/type present, only one present, neither present, schema information, description/config version combinations |
| `foundation/removal-checks.ts` | existing cases plus: no Communication, pre-existing empty network, private content, one surviving ConnectedAP, private ConnectedAP decoy |
| `foundation/removal-plan.ts` | preserve vs delete LNodes, multiple IEDs, each affected network choice, Communication choice, summary fields, edit order, empty selection |

### 10.1 The `scl-lib` LNode scope bug

The SCL schema declares a separate uniqueness key for the direct `LNode`
children of each container, for example `uniqueLNodeInConductingEquipment`
selects `./scl:LNode` and compares `lnInst`, `lnClass`, `iedName`, `ldInst` and
`prefix`. `scl-lib` instead groups LNodes by
`ln.closest('Bay, VoltageLevel, Substation')`. That scope is too wide for an
LNode below a `ConductingEquipment`, `Function`, `SubFunction`, `EqFunction`
or `GeneralEquipment`.

Concrete case:

```xml
<Bay name="B1">
  <ConductingEquipment name="QA1">
    <LNode iedName="None" ldInst="L" lnClass="XCBR" lnInst="1"/>
  </ConductingEquipment>
  <ConductingEquipment name="QB1">
    <LNode iedName="IED1" ldInst="L" lnClass="XCBR" lnInst="1"/>
  </ConductingEquipment>
</Bay>
```

Remove `IED1` with `preserveLNodes: true`.

- Schema-correct result: `QB1` keeps its LNode with `iedName="None"`, because
  the uniqueness key is checked inside `QB1` only.
- `scl-lib` result: both LNodes have the nearest scope `Bay B1`. The cache from
  `QA1` already holds `XCBR|1|L|`, so `QB1`'s LNode gets a `Remove` edit and is
  silently lost.
- The existing `duplicateLNodes` fixture does not catch this because all LNodes
  are inside one `ConductingEquipment`.

Severity is medium: the result stays schema-valid, but engineering data is lost
without a warning. It only occurs when a Bay (or higher scope) contains a
matching unbound LNode in one container and a bound LNode in another.

Options:

| Option | Work | Result | Risk |
|---|---|---|---|
| A. Report upstream only | File an issue with the example; keep `removeIED(..., { preserveLNodes: true })` | No code change in this branch; bug remains until `scl-lib` releases a fix | Known silent data loss stays |
| B. Local `foundation/l-node.ts` | Call `removeIED` for the non-LNode edits, filter its LNode edits, add a pure detach function keyed by `ln.parentElement` | Correct per-container merge; regression tests; ~50 lines to maintain | A second implementation of the LNode rule; must be removed when `scl-lib` is fixed |
| C. Patch `scl-lib` and bump the dependency | Change `getLNodeScopeElement` to `ln.parentElement`, release `scl-lib`, update the plugin | Correct for every consumer | Outside this repository; release timing blocks this branch |

Recommendation: **B for this branch, plus an upstream issue**. The plugin's
central promise is that it preserves LNodes, so leaving a known silent deletion
is not acceptable for a completed migration. The function is pure, small and
testable, and the rest of the destructive work still comes from `scl-lib`. When
`scl-lib` is fixed, delete the local function and pass `preserveLNodes: true`
again.

Implementation sketch for B:

- `detachLNodes(doc, iedNames)` returns `SetAttributes | Remove` edits.
- For each public bound LNode under `Substation`, use `ln.parentElement` and the
  key `lnInst|lnClass|ldInst|prefix`.
- Start the key set from existing `LNode[iedName="None"]` in the same parent.
- First bound LNode for a key becomes `iedName="None"`; later bound LNodes with
  the same key in the same parent are removed.
- Ignore non-public LNodes.
- `removeIEDs()` computes these edits once for the whole selection, calls
  `removeIED(..., { preserveLNodes: false })` for each IED and filters out its
  LNode edits, then dispatches the local LNode edits in the same squashed
  operation.
